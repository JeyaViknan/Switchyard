# M1 — Gateway ops refactors

## What was built
`/livez` and `/readyz` as separate endpoints (`/health` kept as an alias),
build identity on `/readyz` plus a `switchyard_build_info` gauge, `kind:
synthetic|external` on `/v1/providers`, `stop_grace_period: 40s`, and the base
image pinned by digest. 16 new tests.

## Why
One health endpoint answers two questions with opposite consequences: failing
readiness should stop traffic, failing liveness should restart the container.
Draining is where they disagree — the gateway is deliberately refusing new work
while finishing in-flight streams, and a restart then destroys exactly what the
drain protects.

`stop_grace_period` is the same bug from the other side: drain is 30s, Docker's
default SIGKILL is 10s, so every graceful shutdown was being shot a third of
the way through.

## Interview questions

**What's the difference between liveness and readiness?** Readiness gates
traffic; liveness gates restarts. They differ during drain and during slow
startup. `/livez` reads no scheduler state on purpose — a liveness probe a busy
subsystem can fail will restart a process that was about to recover.

**How do you know which version is deployed?** `/readyz` reports `git_sha` from
a Docker build arg, and the deploy smoke test compares it to the SHA it shipped
— in the same request that proves the gateway is up. A rollback is confirmed
the same way. There's also a `switchyard_build_info{version,git_sha} 1` gauge,
so a dashboard can answer "did errors rise when the sha changed?".

**Why pin the base image by digest?** A tag moves. The base image is the layer
with the most CVEs and the least visibility, and an unpinned one turns a
reproducible build into a coincidence. The pin is the multi-arch index digest,
so amd64 and arm64 both still resolve.

**A test broke when you added unrelated tests — what did you do?** Measured it.
The load generator's p99 scheduling lag goes from 0.66% of request latency
alone to 7.54% behind the full suite, against a 5% threshold — it was asserting
a property of the host, not of the system. Marked it `slow` and split
`make test-all` into two pytest processes so timing tests get a fresh
interpreter. No assertion was weakened.
