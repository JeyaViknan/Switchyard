# M4 — Production Compose and prod-local

## What was built
`deploy/compose.prod.yml` (five services by `${IMAGE_TAG}`, nothing builds),
`switchyard.prod.toml` with placeholder digests, a company example,
`prometheus.prod.yml`, `smoke.sh`, `scripts/{dev-secrets,mint-prod-keys}.sh`,
and `make prod-local` — the rehearsal and the demo fallback.

## Why it looks like this
Paths are **variables**, not an override file. Compose *merges* `env_file`
lists rather than replacing them, so a laptop override could not swap
`/etc/switchyard` for `./local` — it demanded both. One definition of the
topology beats two that must be kept in step.

Credentials are one env file per service, so the gateway never sees the
console password and Grafana never sees the key pepper. Prometheus reads its
scrape key from a *file*, because the config is in git and the key is not.
Grafana runs anonymous **Viewer**: port 3000 is open to the internet and
anonymous Admin would let anyone edit the alerting that holds the Telegram
token.

## Measured, under the noisy-neighbour flood

| Container | Peak memory | Peak CPU |
|---|---|---|
| grafana | 98 MiB | 2.2 % |
| console | 52 MiB | 29.2 % |
| gateway | 50 MiB | 20.0 % |
| fleet | 48 MiB | 25.8 % |
| prometheus | 28 MiB | 0.3 % |
| **total** | **276 MiB** | — |

The box has 1 GiB plus 2 GiB of swap, so the stack peaks at about 27 % of
RAM. **No `mem_limit`s** — the handover said measure first and the
measurement says they would be solving a problem that does not exist. Caveat:
this was an Apple Silicon laptop, so memory should carry across but the CPU
percentages are against different cores.

## Interview questions

**Why no separate laptop compose file?** Compose merges `env_file` lists
instead of replacing them, so an override would require both paths to exist.
Making the location a variable keeps one topology definition.

**Why build the image outside Compose?** Three services are three entrypoints
into one image. Three `build:` stanzas for the same tag had buildx racing
itself — "image already exists". Building once and only running is also what
the instance does, so prod-local now differs from production in exactly one
way: where the image came from.

**How did you size the memory limits?** I measured instead of guessing: 276
MiB peak against 1 GiB under the demo's own worst case, so no limits. If it
had been close, Grafana would have been the one to cap.

**Why is the queue depth 40 and not 256?** 256 absorbed the demo's flood by
queueing instead of refusing it, which hid admission control entirely — the
console's own scenario check reported "the flood never exceeded capacity".
The config change is what that verdict asked for.
