# M0 — Making CI green

## What was built
`pythonpath = ["."]` in `[tool.pytest.ini_options]`, plus CI hardening: pinned
runner (`ubuntu-24.04`), every action pinned to a commit SHA on a current
major, an environment dump, and a separate collection step.

## Why
CI ran `pytest -q`; the Makefile ran `python -m pytest -q`. Only `-m` prepends
the working directory to `sys.path`, and eleven call sites do
`from tests.conftest import ...`, which needs the repo root importable. The
module-scope one in `test_reliability.py` aborted collection — exit 2, four
seconds, before a single test ran. Declaring the path in configuration makes
the suite behave the same however it is launched; pointing CI at `python -m`
would have gone green while leaving it fragile for anyone typing `pytest`.
Fixing that let the `bench` job run for the first time and it failed twice
more, both the same shape: the Makefile hardcoded `.venv/bin/python`, which CI
does not have, and the benchmark printer formatted `scheduling_lag_ratio` with
`:.3f` when `summarize` returns None for it. Full write-up in
`docs/decisions.md`.

## Interview questions

**Passed locally, red in CI for two months — how did you find it?** I compared
the two *invocations*, not the two environments: same fresh venv, `pytest -q`
failed with `ModuleNotFoundError: No module named 'tests'`, `python -m pytest`
passed 356.

**Why not just change CI to `python -m pytest`?** That fixes the symptom. The
defect was depending on an implicit side effect of the launcher, so I made the
requirement explicit instead.

**What does exit code 2 mean, and why did ruff and mypy stay green?**
`INTERRUPTED` — collection failed, so zero tests ran and CI was reporting on
nothing. ruff and mypy never import the package, so an import error can only
appear at collection; that now has its own step.

**Why pin the runner and action SHAs?** `ubuntu-latest` was migrating to
Ubuntu 26 — the environment could change with no commit to blame. A mutable
tag is also a supply-chain risk: a tag can be repointed, a SHA cannot.

**What was the common thread?** All three failures were the build assuming a
developer's machine: how pytest is launched, that a `.venv` exists, that a
benchmark window always has data. CI is the environment that doesn't share
those assumptions, which is the whole reason to have it.
